## 1. Primitives

### 1.1 Money
```kotlin
@JvmInline value class CurrencyCode(val code: String)          // ISO 4217 alpha-3, validated against table
data class Money(val minor: Long, val currency: CurrencyCode)   // minor units, signed
```
- Precision (`minorDigits`) comes from a built-in ISO 4217 table: PHP 2, USD 2, JPY 0, KWD 3, and so on.
- `plus`/`minus` require equal currencies (otherwise `CurrencyMismatch`) and use `Math.addExact`/`subtractExact`.
- Multiplication by an integer quantity uses `multiplyExact`. There is **no** multiplication or division by fractional numbers on `Money`.
  Ratios go through `Allocation.split` (§1.3) or `RateMath` (§1.4).
- Parsing user input: a string → `BigDecimal` (scale ≤ minorDigits, otherwise a validation error, never silent rounding) → `minor`.
  Grouping separators `,` and the `₱` symbol are accepted and stripped. A negative sign is rejected in amount fields because the
  transaction type carries the direction.
- Formatting: PHP `₱1,234.56`, negative `−₱1,234.56` (U+2212). The formatter is locale-aware, with en-PH as the default.

### 1.2 Dates and time
- `txnDate: LocalDate` is the **calendar date of the transaction in the user's zone**. All period attribution uses it.
- `occurredAt: Instant?` is an optional precise time, kept for ordering and display.
- `zone: ZoneId` is the user setting, default `Asia/Manila`. Changing the zone does **not** change stored `txnDate`s.
- "Today" always comes from an injected `Clock` and the user zone. Domain code never calls `LocalDate.now()` without a clock.

### 1.3 Allocation (deterministic split)
`split(total: Long, weights: List<Pair<Key, Long>>): Map<Key, Long>`, using **largest-remainder** rounding:
1. `W = Σ weights` (must be > 0, all weights ≥ 0).
2. For each i: `q_i = floor(|total| × w_i / W)`, `r_i = (|total| × w_i) mod W` (exact `BigInteger` / `multiplyHigh` to avoid overflow).
3. `R = |total| − Σ q_i` (always `0 ≤ R < n`).
4. Give +1 to the `R` items with the largest `r_i`. Ties go to the smallest `Key` in stable sort order (ids, then list position).
5. Apply `sign(total)` to every share.

Guarantee: `Σ shares == total` exactly, and the result is identical on every run and device.

**EX-1**: split ₱100.00 (10000) by bp [3333, 3333, 3334] → [3333, 3333, 3334].
**EX-2**: split ₱100.00 equally across A, B, C → [3334, 3333, 3333] (A wins the tie by key order).
**EX-3**: split −₱0.05 (−5) equally ×2 → [−3, −2].

### 1.4 Rates
- Percentages and interest rates are **basis points** (`Int`, 1 bp = 0.01 %).
- `RateMath.applyBp(amount, bp, rounding)` computes `amount × bp / 10_000` in `BigDecimal` with an explicit `RoundingMode`
  (default `HALF_EVEN`) and returns `Long` minor units. This is the single place fractional money math exists.

**EX-4**: 2.5 % (250 bp) of ₱1,234.56 → 123456 × 250 / 10000 = 3086.4 → HALF_EVEN → 3086 (₱30.86).

### 1.5 Identifiers
UUIDv7 (time-ordered) strings, generated by an injected `IdGenerator`. Ids are created on the device and never reused.

## 2. Ledger accounts

Every balance-holding thing is a **ledger account** with a `class`:

| Class | Examples | Balance sign convention | User-visible as |
|---|---|---|---|
| `ASSET` | Cash, bank, e-wallet, savings account | + = money held | Account |
| `LIABILITY` | Credit card, loan, borrowed money | − = amount owed | Account / Debt |
| `INCOME` | Salary, Freelance (categories) | − = income earned | Income category |
| `EXPENSE` | Food, Transport, Interest & fees | + = money spent | Expense category |
| `EQUITY` | `equity:opening`, `equity:adjustment`, `equity:fx` | system-only | Hidden |

ASSET and LIABILITY are **real** accounts. INCOME, EXPENSE and EQUITY are **nominal**.
Categories (with subcategories) are INCOME- or EXPENSE-class ledger accounts. Real accounts have one fixed currency.
Nominal accounts are currency-agnostic, because every entry carries its own currency.

System accounts created at first run (not deletable, not archivable): `equity:opening`, `equity:adjustment`, `equity:fx`,
`expense:interest_fees` (default category for debt interest, renamable), `income:uncategorized`, `expense:uncategorized`.

## 3. Transactions and entries

A **transaction** is a header (type, status, dates, description, merchant, notes, reference, source, links). It owns
**≥ 2 entries** `(ledgerAccountId, amountMinor, currency)`.

### 3.1 Core invariants (enforced in `:domain` before any write, and re-checked by DB integrity tests)
- **I-1 Zero sum:** for every transaction and every currency, Σ entries = 0.
- **I-2 Real-account currency:** an entry on a real account has that account's currency.
- **I-3 No zero entries:** `amountMinor ≠ 0`.
- **I-4 Type shape:** entries match the type's template (§3.3).
- **I-5 Balances are derived:** balance(account, D) = Σ entries on the account where txn.status = POSTED, txn not deleted,
  and txn.txnDate ≤ D. No stored balance is authoritative.
- **I-6 Immutable history:** a change to a POSTED transaction writes a revision (§3.6). Hard deletion of a POSTED transaction is impossible.

### 3.2 Statuses
`PENDING` (shown in a separate pending balance, excluded from the posted balance and from reports by default) and `POSTED`.
Deletion is a separate `deletedAt` tombstone, not a status.

### 3.3 Transaction type templates

Notation: `A` = amount > 0. `acct` = real account. `cat` = category ledger account. Splits allow several category entries whose parts sum to `A`.

| Type | Entries | Validation | Report classification |
|---|---|---|---|
| `INCOME` | acct **+A**; income cat(s) **−parts** | acct ASSET or LIABILITY (e.g., card cashback) | Income |
| `EXPENSE` | acct **−A**; expense cat(s) **+parts** | acct ASSET or LIABILITY | Spending |
| `TRANSFER` | from **−A**; to **+A** | two different real accounts, same currency | Not income/spending |
| `TRANSFER` (cross-currency) | from **−A₁** (c₁); `equity:fx` **+A₁** (c₁); `equity:fx` **−A₂** (c₂); to **+A₂** (c₂) | c₁ ≠ c₂; user enters both amounts (implied rate stored for display only) | Not income/spending |
| `SAVINGS_CONTRIBUTION` | as TRANSFER | destination account type = SAVINGS | Savings movement |
| `SAVINGS_WITHDRAWAL` | as TRANSFER | source account type = SAVINGS | Savings movement |
| `REFUND` | acct **+A**; expense cat **−A** | if `refundOfTxnId` set: original is EXPENSE, same currency, cat defaults to original's, Σ refunds ≤ original amount | Reduces spending |
| `REVERSAL` | the exact negation of every entry of the original | `reversesTxnId` required; original POSTED, not deleted, not a REVERSAL, not already reversed | Nets the original's classification |
| `BALANCE_ADJUSTMENT` | acct **±A**; `equity:adjustment` **∓A** | created by reconciliation or explicitly | Adjustment (excluded from income/spending) |
| `DEBT_DISBURSEMENT` | asset acct **+A**; liability **−A** | liability account linked to a debt | Not income |
| `DEBT_PAYMENT` | asset acct **−(P+I+F)**; liability **+P**; `expense:interest_fees` (or chosen cat) **+(I+F)** | P ≥ 0, I ≥ 0, F ≥ 0, P+I+F > 0 | Principal: not spending. Interest/fees: spending |
| `OPENING_BALANCE` | acct **±A**; `equity:opening` **∓A** | at most one per account, system-created | Excluded |

Credit-card usage follows from the templates:
- A purchase is an EXPENSE from the LIABILITY account. The balance becomes more negative (more owed).
- A card payment is a TRANSFER from bank to card. Spending is counted once, at purchase (Q-06 default).
- An installment purchase on a card is an EXPENSE from the card account. Installment tracking is a debt schedule (§7).

**EX-5 (AC-CORE-1)** — Transfer ₱2,000 GCash → BPI. Entries GCash −200000, BPI +200000.
GCash balance −₱2,000; BPI +₱2,000; income 0; spending 0; net worth unchanged.

**EX-6** — Card purchase ₱1,200 then full payment from BPI. Card: −120000 then +120000 = 0. BPI −120000.
Spending for the period = ₱1,200 (once). Net worth after both = −₱1,200 vs. before.

**EX-7 (AC-CORE-7)** — Expense ₱500 Food, then linked refund ₱200. Food spending = 50000 − 20000 = ₱300. Income unchanged.

**EX-8** — Loan payment ₱1,100 = ₱1,000 principal + ₱100 interest. BPI −110000; Loan +100000; Interest & fees +10000.
Spending +₱100 only.

### 3.4 Report classification (single source of truth)
For a date range [S, E] (inclusive, by `txnDate`), POSTED, not deleted:
- **Income total** = −Σ entries on INCOME-class accounts.
- **Spending total** = Σ entries on EXPENSE-class accounts. Refunds and reversals reduce it automatically.
- **Adjustments** = Σ entries on `equity:adjustment` (shown separately, never as income or spending).
- **Transfers / savings movements** = shown in cash-flow reports only. They never touch nominal accounts, so they cannot leak into income or spending.
- **Net cash flow** of a real account set = Σ entries on those accounts.

**EX-9 (AC-CORE-2, ledger identity)** — because of I-1, for any set of transactions:
Σ(all real account balances) = −Σ(all nominal entries) = Σ opening + income − spending + adjustments.
FX equity appears only when currencies are mixed. Then the identity holds per currency, including `equity:fx`.
Phase 4 property test: 10,000 random valid operation sequences; assert the identity per currency after every step.

### 3.5 Reversal timing
A reversal carries its own `txnDate` (default: today; the user may set the original's date). If the dates fall in different
periods, the original stays in its period and the reversal is attributed to its own period. This is intended (it reflects when
the bank reversed the charge). To *correct* a mistake, the user **edits** the transaction (a revision), not reverses it.

### 3.6 Edits, deletes, audit
- **Edit** of a POSTED transaction: one DB transaction replaces the header fields and the entry set, writes `txn_revision`
  (revision_no + 1, before/after snapshots, device id, timestamp, optional reason), and bumps `version`. Reports always reflect the current state.
- **Delete**: sets `deletedAt`, writes a revision. The transaction disappears from balances and reports and stays in the audit log. It can be restored (another revision).
- PENDING → POSTED is an edit with a revision.
- Restrictions: a transaction that is reversed or refunded cannot have its amount or currency changed without first removing
  the dependent link (prevents orphaned refund > original). An imported transaction can be edited, and it stays linked to its batch.
- **Archived accounts and categories on edit** (owner decision 2026-11-07): an archived account or category stays valid in
  an edit of a transaction that *already* references it, so the amount, date or description of an old transaction can always
  be corrected. It is still rejected (`ACCOUNT_ARCHIVED`, `CATEGORY_ARCHIVED`) for a new transaction and as a newly chosen
  target of an edit. `EntryTemplates(directory, allowArchived = ids of the edited transaction's entries)` implements this.

**EX-10 (AC-CORE-8)** — Expense ₱500 edited to ₱450: revision 2 stored with before 50000 / after 45000. Spending report shows ₱450.

## 4. Balances shown to users (ACC-05)

| Balance | Definition |
|---|---|
| **Current (calculated)** | I-5 with D = today |
| **Pending** | Σ entries of PENDING transactions on the account (shown as "+/− pending") |
| **Projected** | Current + entries of POSTED transactions dated after today (future-dated) |
| **Reconciled** | Statement balance of the latest reconciliation, with its date |
| **Statement balance** | Last closing balance from an import or a user-entered reconciliation, with "as of" date |

The UI always labels which one is shown. The dashboard total uses **Current** only.

### 4.1 Reconciliation (ACC-06, IMP-10)
Input: account, as-of date D, statement balance B. Compute C = balance(account, D). Difference Δ = B − C.
If Δ ≠ 0 the user may (a) review transactions, or (b) create a BALANCE_ADJUSTMENT of Δ dated D. A reconciliation record
stores B, C, Δ, and the optional adjustment id.

## 5. Budgets

### 5.1 Periods (BUD-01/02)

| Kind | Parameters | Period k |
|---|---|---|
| `WEEKLY` | anchorDate | [anchor + 7k, anchor + 7k + 6] |
| `BIWEEKLY` | anchorDate | [anchor + 14k, anchor + 14k + 13] |
| `EVERY_N_DAYS` | anchorDate, n (1..366) | [anchor + nk, anchor + nk + n − 1] |
| `MONTHLY` | anchorDate, anchorDay d (1..31) | start_k = clampDay(d, month(anchor) + k); end_k = start_{k+1} − 1 |
| `SEMI_MONTHLY` | anchorDate, days d₁ < d₂ (e.g., 15 and 31 = "15th & end of month") | starts at clampDay(d₁,m) and clampDay(d₂,m) each month; end = next start − 1 |
| `CUSTOM_ONCE` | start, end | single period |

`clampDay(d, yearMonth) = min(d, yearMonth.lengthOfMonth())`. Periods start at the first start ≥ anchorDate. Dates before the
first period start belong to no period of that budget.

`SEMI_MONTHLY` is an addition (BUD-01 amendment) because PH salaries are commonly paid on the 15th and the 30th/end of month.

**Lookup is closed-form, not iterative.** For MONTHLY: m = yearMonth(D); s = clampDay(d, m); if D < s then s = clampDay(d, m − 1); end = clampDay(d, month(s) + 1) − 1.

**EX-11 (BUD-02)** — MONTHLY d = 5, D = 2026-12-04 → period 2026-11-05 … 2026-12-04. D = 2026-12-05 → 2026-12-05 … 2027-01-04.
**EX-12 (AC-CORE-5)** — MONTHLY d = 31 from 2026-01-31: 01-31…02-27, 02-28…03-30, 03-31…04-29, 04-30…05-30.
For 2028 (leap year): 01-31…02-28, 02-29…03-30.
Property test: across 10 years for every d ∈ 1..31, the periods are contiguous, non-overlapping, and each contains exactly one start.
**EX-13 (AC-CORE-6)** — A transaction at 2026-12-04T23:59 Asia/Manila has txnDate 2026-12-04, so it is in the Nov 5–Dec 4 period. At 2026-12-05T00:00 it falls in the next period.
**EX-14** — WEEKLY anchored on 2026-12-28 crosses the year boundary: 12-28…2027-01-03.

**Changing a budget's period rule:** periods that already have allocations keep their stored dates. The new rule applies
from the day after the current period ends. The current period is never split silently.

### 5.2 Budget scope
A budget includes a set of **categories** (expense, optional income), and optionally a set of **accounts** (default: all).
A transaction counts in budget B's period P if its txnDate ∈ P, it is POSTED and not deleted, and its entries touch B's
categories (and B's accounts, when an account filter is set). Only the category entries count, so a split transaction contributes only its in-scope parts.

### 5.3 Overlapping budgets (BUD-04)
- Within one budget, every date belongs to at most one period, so a transaction is counted at most once.
- Across budgets, a transaction may count in several budgets. Each budget is an independent view.
- **No screen or report ever adds up totals of different budgets.** Global reports read the money ledger directly, never budgets.

### 5.4 Allocation ledger (BUD-05/06, SAV-02)
Buckets: `UNALLOCATED(budget, period)`, `CATEGORY(budget, period, cat)`, `GOAL(goal)`.
An **allocation group** is one user action. Its entries sum to zero, except the single-sided kinds `FUND` and `GOAL_DIRECT` (below).

| Kind | Entries | Notes |
|---|---|---|
| `FUND` | UNALLOCATED +X | Manual funding (income mode MANUAL) |
| `ALLOCATE` | UNALLOCATED −X; CATEGORY +X | Fixed or computed from % (split §1.3) |
| `REALLOCATE` | CATEGORY(a) −X; CATEGORY(b) +X (or ↔ UNALLOCATED) | Mid-period adjustment |
| `GOAL_CONTRIBUTE` | UNALLOCATED −X (or CATEGORY −X); GOAL +X | Savings from the budget pool |
| `GOAL_WITHDRAW` | GOAL −X; UNALLOCATED +X | Requires confirmation |
| `GOAL_DIRECT` | GOAL ±X | Earmark from "free money" without a budget |
| `GOAL_TRANSFER` | GOAL(a) −X; GOAL(b) +X | Reallocation between goals |
| `ROLLOVER` | CATEGORY(P) −R; CATEGORY(P+1) +R | At period close |
| `SWEEP` | CATEGORY(P) −R; GOAL +R | Rollover policy "sweep to savings" |

**Budget funding** for a period, by income mode:
- `TRACKED`: −Σ in-scope income entries in the period (derived, not stored).
- `FIXED`: a configured amount.
- `MANUAL`: Σ `FUND` entries.

Derived values:
- **Available to budget(P)** = funding(P) + Σ allocation entries on UNALLOCATED(P). Can be negative (over-allocated); shown in red.
- **Category allocated(P, c)** = Σ allocation entries on CATEGORY(P, c).
- **Category spent(P, c)** = in-scope spending on c (and its subcategories) in P.
- **Category remaining** = allocated − spent (negative = overspent).
- **Goal allocated(g)** = Σ allocation entries on GOAL(g), across all budgets and direct earmarks.

**EX-15 (AC-CORE-3 / SAV-02)** — Funding ₱30,000 (TRACKED salary). GOAL_CONTRIBUTE ₱5,000 → Available ₱25,000; Goal +₱5,000;
spending unchanged; money-ledger balances unchanged.

**EX-16** — Percentage allocation of ₱25,000 at [Food 3000 bp, Transport 1500 bp, Bills 5500 bp] → 750000, 375000, 1375000 (sum 2500000).

### 5.5 Rollover at period close (BUD-07)
A period closes lazily: when the first operation needs the next period, or when the user closes it explicitly. Closing is
**idempotent**, keyed by (budget, period, category). For each category with remaining R:

| Policy | R > 0 | R < 0 |
|---|---|---|
| `EXPIRE` (default) | nothing (leftover lapses) | nothing |
| `CARRY` | ROLLOVER +R to next period | ROLLOVER −|R| only if `carryNegative`, else nothing |
| `SWEEP_TO_GOAL` | SWEEP R to the configured goal | as CARRY's negative rule |
| `MANUAL` | leftover kept in a "to reassign" list until the user acts | as CARRY's negative rule |

**Implementation decisions (Phase 4, 2026-11-05; `RolloverPlanner`, `BudgetService`):**
- A carried overspend (CARRY with `carryNegative`) starts the next period's category at a negative allocation. This system-written
  ROLLOVER is the only way a category bucket can be negative; user actions still cannot make it negative.
- CARRY with no next period (CUSTOM_ONCE budget) puts a positive leftover on the "to reassign" list instead of lapsing silently.
- SWEEP_TO_GOAL into a goal that is paused/archived or would exceed its linked-account cap goes to "to reassign" instead.
- "To reassign" leftovers are resolved by the user (carry to next period, sweep to a goal, or expire). Each resolution is recorded
  under the same idempotency key as an automatic rollover (`rollover:{period}:{category}`); "expire" is a ROLLOVER group with no entries.
- TRACKED funding counts the budget's own income categories; if the budget has none, it counts all income in scope.
- A budget may not contain both a category and one of its subcategories (spending of subcategories is counted under the parent),
  so nothing is counted twice within a budget. Income categories are tracked only (mode NONE, policy EXPIRE).
- Contributions are allowed to ACTIVE and ACHIEVED goals; PAUSED and ARCHIVED goals only release money.

Late-recorded transactions (dated in a closed period) recompute that period's figures. Rollover entries already created are
**not** silently changed. The UI shows "period changed after close: R was X, now Y" and offers a correcting REALLOCATE.

## 6. Savings goals (SAV-01..04)
- Goal: name, target (Money), optional target date, status, notes, optional linked real accounts.
- **Allocated** = §5.4 Goal allocated. **Progress** = min(allocated / target, 100 %), displayed with floor rounding.
- **Free money** (dashboard) = Σ Current balance of ASSET accounts flagged *spendable* − Σ goal allocations that are not linked to accounts.
- **Linked goals (SAV-03):** if goal g is linked to accounts L, then Σ allocations of all goals linked to the same accounts must not exceed
  Σ balance(L). A contribution that would exceed it is rejected with an explanation.
  Physical moves are money-ledger SAVINGS_CONTRIBUTION transfers, optionally with a linked GOAL_CONTRIBUTE in one user action
  (same DB transaction, `relatedTxnId`).
- **Net worth reads only the money ledger** (§8), so allocations can never inflate it.
- **Withdrawal / reallocation (SAV-04):** requires explicit confirmation in the UI. The allocation group stores
  previous allocation, new allocation, amount, source bucket, destination bucket, date, optional reason, and optional related txn.

**EX-17** — Goal "Laptop" linked to BPI Savings (balance ₱20,000). Allocations ₱15,000 OK. A further ₱6,000 is rejected
(would be ₱21,000 > ₱20,000). Net worth includes ₱20,000 once.

## 7. Debts (DEBT-01..03)
- A debt is a LIABILITY account plus terms: original amount, start date, interest rate (bp, informational unless a schedule is generated), payment frequency, installment amount, total installments, due day, counterparty, status.
- **Outstanding** = −balance(liability) (I-5). It is never stored separately.
- **Payment history** = DEBT_PAYMENT transactions on the liability.
- **Installment schedule** (optional): generated rows (due date, amount due) linked to payments when recorded. Remaining installments = unpaid schedule rows.
- Interest calculation is **user-entered per payment** (split P / I / F). The app does not compute lender interest
  automatically, because PH lenders use varied methods (add-on, diminishing). A schedule calculator for standard amortization
  may be added later and must be labeled as an estimate.

## 8. Net worth (NW-01/02)
NW(D) = Σ balance(D) over real accounts with `includeInNetWorth` (assets +, liabilities −) + Σ latest valuation ≤ D of asset records with `includeInNetWorth`.
Mixed currencies are shown per currency. A converted total appears only with a user-entered rate and is labeled "converted at rate X on date Y".
History (NW-02): computed on demand per month-end from the ledger plus valuations. It can be cached in a snapshot table that is verified against recompute in tests.

## 9. Recurring rules (bills, subscriptions, recurring transactions, expected income)
- Rule: kind (BILL, SUBSCRIPTION, RECURRING_TXN, EXPECTED_INCOME), amount (with `isEstimate`), frequency
  (WEEKLY, BIWEEKLY, MONTHLY(d), SEMI_MONTHLY(d₁,d₂), QUARTERLY(d), YEARLY(m,d), EVERY_N_DAYS), anchor date, end date, account, category, reminder offset.
- Occurrences are materialized for a rolling window (today − 31 d … today + 62 d), unique by (rule, dueDate), and recomputed when the rule changes (future occurrences only).
- An occurrence becomes PAID **only** when it is linked to a real transaction, either created from it or matched to an existing one (BILL-02).
  Overdue = unpaid and dueDate < today (derived).
- `RECURRING_TXN` with `autoPost` (manual source only, opt-in) creates the transaction on or after the due date when the app runs. Each auto-posted transaction is idempotent by (rule, dueDate).

## 10. Categorization rules (CAT-03)
Ordered rules: match on description/merchant (EQUALS, CONTAINS, STARTS_WITH; case- and accent-insensitive normalized text),
optional amount range, optional account. They produce a category in SUGGEST or AUTO mode. AUTO applies only at creation and import time and is
shown in the import preview. Rules never modify existing transactions retroactively unless the user runs "apply rule to past transactions" with a preview.

## 11. Error model
Domain functions return `Result`-like sealed types (`DomainError.Validation(field, code)`, `CurrencyMismatch`,
`InvariantViolation`, `NotFound`, `Conflict`). They never throw for expected business errors. Arithmetic overflow throws, and the
use-case boundary converts it to `DomainError.Overflow`.
